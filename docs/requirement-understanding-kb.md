# মানুষের Requirement বোঝার জ্ঞান-ভিত্তি (Requirements Understanding KB)

**উদ্দেশ্য:** একাধিক কাস্টমারের ভিন্ন ভিন্ন requirement যেন আমাদের সিস্টেম (SupremeAI) সঠিকভাবে বুঝতে পারে, দ্ব্যর্থ চেনে, সঠিক প্রশ্ন করে এবং একবার শেখা জ্ঞান পরবর্তী কাস্টমারের কাজে লাগাতে পারে।
**সংগঠিত ডেটা:** `requirement-understanding-kb.json` (schema, প্রশ্ন-ব্যাংক, prompt টেমপ্লেট) — এই দুটি ফাইল একসাথে ব্যবহার করুন।

---

## ১. মূল দর্শন: মানুষ requirement কীভাবে বলে

মানুষ প্রায় কখনো "requirement spec" দেয় না — তারা **সমস্যা, আবেগ, উদাহরণ ও ইচ্ছা** বলে। সিস্টেমকে এই ৭টি সত্য গ্রহণ করতে হবে:

1. **সমাধান আর সমস্যা মেশে যায়** — কাস্টমার বলবে "একটা ড্যাশবোর্ড দরকার" (সমাধান); প্রকৃত requirement হলো "আমি জানতে চাই প্রতিদিন কত অর্ডার আসছে" (সমস্যা)। → সবসময় জিজ্ঞেস করুন: **"এটা দিয়ে আপনি আসলে কী সিদ্ধান্ত নিতে চান / কোন ব্যথা কমছে?"**
2. **শব্দের অর্থ ব্যক্তিভেদে বদলায়** — "দ্রুত" = ২০০ms নাকি ২ সেকেন্ড? "নিরাপদ" = কোন মানদণ্ডে? → প্রতিটি গুণবাচক শব্দের জন্য **পরিমাপযোগ্য সংজ্ঞা** দরকার।
3. **অন্তর্নিহিত প্রয়োজন অদৃশ্য থাকে** — "লগইন সহজ হোক" মানে হতে পারে SSO, নাকি পাসওয়ার্ড ভুলে গেলে রিসেট — দুটোই নয় হতে পারে (মোবাইলে OTP)।
4. **অগ্রাধিকার অস্পষ্ট থাকে** — সবকিছু "জরুরি" শোনায়। আসল অগ্রাধিকার বোঝা যায় **ট্রেড-অফ প্রশ্নে**: "ডেডলাইন বা ফিচার — কোনটা ছাড়বেন?"
5. **কনটেক্সট ছাড়া requirement বিপজ্জনক** — একই "রিপোর্ট এক্সপোর্ট" ব্যাংকের জন্য আইনগত নথি, ই-কমার্সের জন্য সুবিধা।
6. **পরিবর্তন স্বাভাবিক** — requirement একটি জীবন্ত ডকুমেন্ট; version ও change-reason রাখতে হবে।
7. **"কেন" টেকসই, "কী" পরিবর্তনশীল** — সংরক্ষণের কেন্দ্রে থাকবে goal/problem, feature নয় (feature বদলাবে)।

## ২. Requirement বোঝার ৫-ধাপের চক্র

```
গ্রহণ (Intake) → স্বাভাবিকীকরণ (Normalize) → অস্পষ্টতা শনাক্ত (Ambiguity Scan)
      → স্পষ্টীকরণ (Clarify Loop) → নিশ্চিতকরণ (Confirm & Decompose) → সংরক্ষণ ও পুনর্ব্যবহার
```

**ধাপ ১ — গ্রহণ:** কাস্টমারের মুখের ভাষা আক্ষরিকভাবে রাখুন (`raw_statement`)। অনুবাদ নয় — পরে ভুল হলে মূলটা দরকার হবে।

**ধাপ ২ — স্বাভাবিকীকরণ:** একটি অভিন্ন টেমপ্লেটে ভাগ করুন (JSON ফাইলের `requirement_intake_schema`): লক্ষ্য, সমস্যা, ব্যবহারকারী, সফলতার মাপকাঠি, সীমা, অস্বীকৃত (out-of-scope), স্বীকৃত অনুমান।

**ধাপ ৩ — অস্পষ্টতা শনাক্ত (সবচেয়ে গুরুত্বপূর্ণ):** নিচের ৪টি সিগন্যাল খুঁজুন:
- **গুণবাচক অতিরঞ্জন:** দ্রুত, সহজ, আধুনিক, নিরাপদ, স্মার্ট, সবচেয়ে ভালো, user-friendly
- **অসীম/অনির্দিষ্ট:** unlimited, everything, সব ধরনের, real-time, যত দ্রুত সম্ভব (ASAP), সস্তা, etc.
- **অস্পষ্ট রেফারেন্স:** "যেমন Amazon-এর মতো", "আগের মতোই", "স্ট্যান্ডার্ড ওয়েতে"
- **নিহিত বহু-বিকল্প:** "লগইন", "পেমেন্ট", "অ্যাডমিন প্যানেল", "AI যুক্ত হোক" — প্রতিটির অনেক বাস্তবায়ন আছে

**ধাপ ৪ — স্পষ্টীকরণ লুপ (সর্বোচ্চ ৩ রাউন্ড):** প্রতি রাউন্ডে **৩–৫টি প্রশ্নের** বেশি নয় (কাস্টমার ক্লান্ত হবেন)। প্রশ্নগুলো সবসময়:
- **দ্বি-মুখী/বহু-নির্বাচনী** হোক ("A নাকি B?"), খোলা প্রশ্ন কম ("কী চান?")
- **ট্রেড-অফ প্রশ্ন** হোক — এতে আসল অগ্রাধিকার ফুটে ওঠে
- **একটি প্রশ্নে একটি বিষয়** — নইলে উত্তর অসম্পূর্ণ আসে
- প্রতিটি প্রশ্নের সাথে **কেন জিজ্ঞেস করলাম** তার এক লাইন যুক্ত হোক (কাস্টমার বিশ্বাস পান)

**ধাপ ৫ — নিশ্চিতকরণ:** সম্মতির জন্য ফিরিয়ে বলুন: "আমি যা বুঝেছি…" + **acceptance criteria** (পরীক্ষাযোগ্য বাক্য) + **out-of-scope** তালিকা (এটা দিয়ে পরে ঝগড়া এড়ায়) + **অনুমান তালিকা** ("আমি ধরে নিচ্ছি মোবাইল-ওয়েব হবে, অ্যাপ নয়")।

## ৩. একাধিক কাস্টমার: পুনর্ব্যবহারের স্থাপত্য

### ৩.১ তিন স্তরে জ্ঞান রাখুন
| স্তর | কী থাকে | কার জন্য | আমাদের সিস্টেমে কোথায় |
|---|---|---|---|
| **সার্বজনীন প্যাটার্ন** | requirement প্যাটার্ন লাইব্রেরি (auth, payment, dashboard, reporting, notification…), এস্টিমেশন ইতিহাস, ঘরানার শব্দকোষ | সব কাস্টমার | Knowledge Graph + Qdrant (tenant-agnostic collection) |
| **টেন্যান্ট-প্রোফাইল** | এই কাস্টমারের ঘরানা, পছন্দ/অপছন্দ, অতীত সিদ্ধান্ত (ADR), শেখা ধরন | এক কাস্টমার | `memory_*` sidecar (tenant_id অটো-ইনজেক্টেড) + Supabase |
| **প্রজেক্ট/টাস্ক-স্মৃতি** | নির্দিষ্ট requirement, সিদ্ধান্ত, যা বাদ গেল, ফলাফল | এক প্রজেক্ট | episodic memory (`memory_record_task`, `memory_get_similar_tasks`) |

⚠️ **টেন্যান্ট আইসোলেশন নিয়ম (অপরিহার্য):** কাস্টমার A-এর requirement/ডেটা কখনোই কাস্টমার B-এর কনটেক্সটে retrieval-এ আসবে না। সব similarity-search-এ `tenant_id` ফিল্টার বাধ্যতামূলক; সার্বজনীন প্যাটার্ন লাইব্রেরিতে শুধু **বিমূর্ত/সাধারণীকৃত** জ্ঞান (কোনো কাস্টমারের নাম, দাম, ডেটা নয়)।

### ৩.২ পুনর্ব্যবহারের ৪টি যান্ত্রিকতা
1. **প্যাটার্ন ম্যাচিং:** নতুন requirement এলে প্রথমেই vector search (`qdrant_search` / `memory_search_semantic`) — "এরকম কাজ আগে করেছি?" → সেই অভিজ্ঞতা (`experience_db`, `learning_loop`) থেকে ঝুঁকি, সময় ও প্রশ্ন ধার করুন।
2. **সমান্তরাল ভিন্নতা (variation model):** প্রতিটি প্যাটার্নে `common_core` (সবার জন্য) আর `tenant_variant` (কাস্টমারভেদে) আলাদা রাখুন। কোডে ফর্ক নয় — **কনফিগ/ফিচার-ফ্ল্যাগ/টেমপ্লেট** দিয়ে ভিন্নতা বহন করুন।
3. **সিদ্ধান্ত রেকর্ড (ADR):** "কেন এভাবে করলাম" লিখে রাখলে পরের কাস্টমারের অনুরূপ প্রশ্নের উত্তর সেকেন্ডে আসে; ভুল সিদ্ধান্ত পুনরাবৃত্তি হয় না।
4. **ক্যালিব্রেশন লুপ:** ডেলিভারির পর নথিভুক্ত করুন — আসল সময়/সমস্যা/requirement drift কত হলো। এই ডেটা ভবিষ্যতের এস্টিমেট ও প্রশ্নকে তীক্ষ্ণ করে (এটাই `adaptive_engine`-এর ভূমিকা)।

### ৩.৩ কাস্টমারদের মধ্যে দ্বন্দ্ব
একই ফিচারে দুই কাস্টমারের বিপরীত চাহিদা এলে (যেমন ডেটা রেজিডেন্সি, রিটেনশন সময়): **গোপনীয়তা ও আইন > এক কাস্টমারের সুবিধা > অন্য কাস্টমারের সুবিধা > আমাদের সুবিধা**। দ্বন্দ্ব থাকলে লুকাবেন না — দুই পক্ষকেই ঘোষণা করুন এবং টেন্যান্ট-স্কোপড কনফিগে সমাধান করুন।

## ৪. Requirement থেকে কাজে: বিশ্লেষণ ও বিভাজন

1. **গোল্ডেন থ্রেড:** `requirement_id → task_id → test_id` — প্রতিটি টাস্ক বলবে কোন requirement পূরণ করছে, প্রতিটি টেস্ট বলবে কোন টাস্ক যাচাই করছে (traceability)।
2. **ভাঙার নিয়ম:** বড় requirement → ছোট, স্বাধীনভাবে ডেলিভারযোগ্য টাস্ক; প্রতিটি টাস্কে **acceptance criteria + পরীক্ষার প্রমাণ** থাকবে (আপনার `bridge_work_order`-এ `scopePaths`, `testsEvidence` ফিল্ড ঠিক এই চিন্তাই ধরে)।
3. **DAG ব্যবহার:** `supremeai-core`-এর `DAGPlanner` ইতিমধ্যে টাস্ক-গ্রাফ ও parallel tier বের করে — requirement বিভাজনের আউটপুট সরাসরি সেখানে ফিড করা যায়।
4. **গুণমান গেট (INVEST):** প্রতিটি requirement হোক — **I**ndependent, **N**egotiable, **V**aluable, **E**stimable, **S**mall, **T**estable। "টেস্ট করতে পারছি না" মানে "বুঝতে পারিনি"।

## ৫. সিস্টেমে বসানোর নকশা (আপনার স্ট্যাক অনুযায়ী)

```
কাস্টমার ইনপুট (চ্যাট/টিকেট/ভয়েস)
   → [1] normalize → requirement object (JSON schema)
   → [2] ambiguity_scan → ঝাপসা শব্দ + অনুপস্থিত ঘর শনাক্ত
   → [3] clarify_loop → লক্ষ্যভিত্তিক প্রশ্ন (৩–৫টি/রাউন্ড, ≤৩ রাউন্ড)
   → [4] confirm → সারাংশ + acceptance criteria + assumptions + out-of-scope
   → [5] decompose → DAG tasks (DAGPlanner) + টেস্ট
   → [6] store → knowledge graph + vector (Qdrant) + episodic (experience_db)
   → [7] reuse → পরবর্তী requirement-এ similar-task retrieval + pattern suggestion
   → [8] feedback → ডেলিভারির পর ফলাফল রেকর্ড → মডেল ক্যালিব্রেট
```

**বাস্তবায়ন পরামর্শ:**
- `memory_store_document` + `memory_ingest_document_rag` দিয়ে requirement ডকুমেন্ট ইনজেস্ট করুন; `memory_search_semantic` দিয়ে অনুরূপ অতীত টানুন।
- `memory_remember_fact` দিয়ে টেন্যান্ট-প্রোফাইল সত্য (যেমন "এই কাস্টমার প্রাথমিকতা দেয় ডেটা নিরাপত্তায়") জমা রাখুন।
- requirement object-এ সবসময় `status`, `confidence_score`, `open_questions[]`, `assumptions[]`, `change_log[]` রাখুন — এগুলো ছাড়া পরে "কেন এভাবে হলো" উত্তর দেওয়া যায় না।
- **প্রশ্ন করার থ্রেশহোল্ড:** `confidence_score < 0.8` এবং ব্যবসায়িক ঝুঁকি থাকলে অবশ্যই প্রশ্ন করুন; ঝুঁকি কম হলে **অনুমান লিখে** এগোন ও পরে নিশ্চিত করুন (মানুষ দ্রুততা পছন্দ করেন, তবে অনুমান দৃশ্যমান হতে হবে)।

## ৬. সংক্ষেপে — ১০টি সোনালি নিয়ম

1. প্রথমে **সমস্যা**, পরে সমাধান।
2. প্রতিটি গুণবাচক শব্দকে পরিমাপে রূপান্তর করুন।
3. প্রশ্ন কম করুন, কিন্তু **সঠিক** প্রশ্ন করুন (ট্রেড-অফ > খোলা)।
4. অনুমান লিখুন, লুকাবেন না।
5. out-of-scope তালিকা সবসময় দিন — এটাই পরে ঝগড়া থামায়।
6. acceptance criteria ছাড়া requirement সম্পূর্ণ নয়।
7. goal রাখুন, feature নয় — feature বদলাবে।
8. প্রতিটি সিদ্ধান্তের কারণ (ADR) লিখে রাখুন।
