## ১. সিস্টেম পরিচিতি ও পাবলিক বাউন্ডারি

`Supremeai-bd/supremeai-open` হলো SupremeAI ফেডারেশনের **পাবলিক বাউন্ডারি (Public SSOT)**। 

- **পাবলিক কাজ:** এখানে সব এজেন্ট ও ডেভেলপাররা উন্মুক্তভাবে কাজ করেন (Zero-Credential)।
- **স্বয়ংক্রিয় ব্রিজিং:** পাবলিক রেপোতে অনুমোদিত ও মার্জ হওয়া কাজ সরাসরি এবং নিরাপদ পাইপলাইনের মাধ্যমে প্রাইভেট কোডবেসে স্থানান্তরিত হয়।
- **বাউন্ডারি নিয়মাবলী:** প্রাইভেট কোর ইঞ্জিন (`backend/`, `supremeai-core`) এবং প্রোডাকশন সিক্রেট কোনোভাবেই এই পাবলিক রিপোজিটরিতে অন্তর্ভুক্ত করা যাবে না।

## ২. গেটহাব ওয়ার্কফ্লোজ ডায়েট (CI Topology)

রিসোর্স ও সময় সাশ্রয়ের জন্য এই পাবলিক রিপোজিটরিতে মাত্র **২টি মূল ওয়ার্কফ্লো** রাখা হয়েছে:

| ওয়ার্কফ্লো ফাইল | ভূমিকা ও দায়িত্ব |
|---|---|
| [`.github/workflows/pipeline.yml`](../.github/workflows/pipeline.yml) | **ভ্যালিডেশন ও টেস্ট:** ব্রাঞ্চের নাম যাচাই, ইস্যু রেফারেন্স চেক, অ্যান্টি-ডুপ্লিকেট চেক, সিক্রেট স্ক্যান (Gitleaks), Python ম্যাট্রিক্স (3.10–3.13) এবং MCP Tower টেস্ট রান করে। |

## ৩. কন্ট্রিবিউশন পাথওয়ে (Zero-Admin Policy, §2.1)

অ্যাডমিনের ওপর কোনো নির্ভরতা ছাড়াই (≤ 0.01% অ্যাডমিন হস্তক্ষেপ) স্বায়ত্তশাসিতভাবে কাজ জমা দেওয়ার ৩টি উপায় রয়েছে:

### পাথওয়ে ১: MCP Control Tower Bridge (জিরো-ক্রেডেনশিয়াল)
- **কাদের জন্য:** MCP ক্লায়েন্ট (Claude, Cursor, Antigravity) বা এক্সটার্নাল এআই এজেন্ট।
- **সার্ভার এন্ডপয়েন্ট:** `https://supremeai-mcp-tower.onrender.com/mcp`
- **পদ্ধতি:** এজেন্ট `bridge_work_order`, `bridge_guide` ও `github_read_file` দিয়ে কোড বিশ্লেষণ করে এবং `bridge_submit_patch` টুলের মাধ্যমে কোনো ব্যক্তিগত গিটহাব টোকেন ছাড়াই স্বয়ংক্রিয়ভাবে প্যাচ জমা দেয়।

### পাথওয়ে ২: ফর্ক ও পুল রিকোয়েস্ট (Fork + PR)
- **কাদের জন্য:** সাধারণ ডেভেলপার বা এক্সটার্নাল ওয়েব এজেন্ট।
- **পদ্ধতি:** রিপোজিটরি ফর্ক করুন → নির্দিষ্ট ব্রাঞ্চে পরিবর্তন করুন → `Supremeai-bd/supremeai-open:main`-এ PR তৈরি করুন।

### পাথওয়ে ৩: এফেমেরাল জেআইটি লিজ (JIT Lease)
- **কাদের জন্য:** স্বয়ংক্রিয় স্ক্রিপ্ট বা সিএলআই রানার।
- **পদ্ধতি:** MCP Control Tower অ্যাডমিন সারফেস থেকে ইস্যুকৃত ১ ঘণ্টার অস্থায়ী লিজ টোকেন দিয়ে পুশ করা হয় (রিপোতে `credential_manager.py` নেই)।

## ৪. গুরুত্বপূর্ণ নীতি ও অনুশাসন (Universal Rules)

### 🔹 U4 — জিরো-ডুপ্লিকেট ম্যান্ডেট (Anti-Duplicate PR Mandate)
- কাজ শুরু করার আগে সবসময় সক্রিয় পুল রিকোয়েস্ট চেক করুন (`gh pr list`)।
- একই ইস্যুর জন্য একাধিক সমান্তরাল বা ডুপ্লিকেট PR খোলা **কঠোরভাবে নিষিদ্ধ**।
- পাবলিক রিপোজিটরিতে কাজ সম্পন্ন হলে প্রাইভেট রিপোজিটরিতে ম্যানুয়ালি আরেকটি ডুপ্লিকেট PR খোলা যাবে না।

### 🔹 ক্লেইম-বিফোর-PR নীতি (Atomic Claim Ordering)
- কোড পরিবর্তন বা PR খোলার আগেই ইস্যুতে ক্লেইম থাকতে হবে (`work_claim` টুল বা `<!-- atomic-claim -->` কমেন্ট মার্কার)।
- ক্লেইম ছাড়া PR তৈরি করলে সিআই-এর Claim Gate সেটি স্বয়ংক্রিয়ভাবে বন্ধ করে দেবে (#2644, #2892)।

### 🔹 U8 — স্কোয়াশ কমিট ডকট্রিন (Closing-Keyword Placement)
- GitHub স্কোয়াশ-মার্জের সময় ইস্যু স্বয়ংক্রিয়ভাবে বন্ধ করার জন্য কমিট মেসেজে অবশ্যই `Closes #<issue-number>` উল্লেখ থাকতে হবে। শুধুমাত্র পিআর ডেসক্রিপশনে থাকলে ইস্যু ক্লোজ নাও হতে পারে।

### 🔹 U5/U7 — বোর্ড ফ্রেশনেস রি-চেক (#4177)
- কাজ সমাপ্তি ঘোষণা করার আগে অবশ্যই পুনরায় বোর্ড চেক (`gh pr list`) করুন। টাস্ক চলাকালীন সময়ে নতুন কোনো পিআর বা ইস্যু এসেছে কিনা তা নিশ্চিত হয়ে তবেই চূড়ান্ত রিপোর্ট দিন।

### 🔹 U10 — লুপ-অনুমোদিত স্বায়ত্তশাসন (No Permission-Asking)
- প্রি-কন্ডিশন ঠিক থাকলে অনুমতি না চেয়ে ("Should I proceed?", "শুরু করব?") সরাসরি কাজ সম্পন্ন করে ফ্যাক্ট-বেসড রিপোর্ট পেশ করুন।

## ৫. লোকাল ডেভেলপমেন্ট ও টেস্ট কমান্ড

কোনো কোড পুশ করার আগে লোকালি যাচাই করে নেওয়া বাধ্যতামূলক:

```bash
# ১. বাউন্ডারি স্যানিটেশন গার্ড পরীক্ষা (প্রাইভেট কোড বা সিক্রেট প্রতিরোধ)
python scripts/ci/boundary_sanitization_guard.py --check

# ২. পাইথন টেস্ট স্যুট রান করা
python -m pytest tests/

# ৩. লুপ চুক্তি সমতা পরীক্ষা
python scripts/agents/check_loop_contract_parity.py
```

## ৬. ব্রাঞ্চ ও কমিট নামকরণের নিয়ম

- **ব্রিজ টাস্ক ব্রাঞ্চ:** `bridge/<task-id>` (উদাঃ `bridge-20261016-fix-typo`)
- **কন্ট্রিবিউটর ব্রাঞ্চ:** `fix/<short-slug>` অথবা `feat/<short-slug>`
- **কমিট ফরম্যাট:** Conventional Commits মেনে চলুন (যেমন: `fix(scope): ...`, `docs(guide): ...`) এবং সাথে `Closes #<issue-number>` রাখুন।
