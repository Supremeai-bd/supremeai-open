## What landed (option B, in-repo, this PR)

- **Live probe (zero-credential, 2026-10-29 ~19:45Z):** `GET https://supremeai-mcp-tower.onrender.com/health` → **200/82ms**, body `{"status":"degraded","server":"supremeai-control-tower","version":"1.0.0","services":{"healthy":31,"degraded":2,...}}`. The endpoint exists on the deployed build today; the field merely wires Render's rollout gate to it.
- **Transport-level, by design:** Render health checks pass on 2xx and ignore the body, so the gate discriminates *does the new container boot and serve* — exactly the signal the RCA said was missing ("the NEW container fails to serve, and Render marks the deploy `update_failed` after boot retries" with "no health-check signal"). The tower's own `status: degraded` subsystem view (31/33) does NOT fail the gate; subsystem health is the tower's internal concern, boot liveness is the deploy plane's.
- **The class it closes:** P1 #2211's boot crash (`Tool system_parity_audit is already registered` → `registerAllTools` rejects → server fatal → Render rolls back silently to the 10-24 build) would have surfaced as a failed health check instead of a silent multi-day stale deploy. #2229's third falsification ("Render autoDeploy has no check-gate") is addressed on the health plane; the CI plane is option A below.
- **Sibling status:** `browser/render.yaml` (`supremeai-browser`) **already declares** `healthCheckPath: /health` — the in-repo web-service fleet is now fully gated. The api service (`supremeai-api-ulw0`) is dashboard-managed (no in-repo blueprint); its healthCheckPath fix was routed by the RCA and tracked in #2205's post-redeploy resolution — out of repo scope, noted here only for the fleet picture. `render-worker` is a background worker: Render docs scope health checks to **web services**, so worker coverage is honestly out of B's reach (the scout's own partial-scope note).
