# 📖 রক্ষণাবেক্ষণ এবং অটো-ফিক্স ওয়ার্কফ্লো (`maintenance_pipeline.yml`)

এই ডকুমেন্টটি আমাদের `maintenance_pipeline.yml` ওয়ার্কফ্লোর কার্যকারিতা, বিভিন্ন ধাপ এবং এর পেছনের মূল ধারণাগুলো ব্যাখ্যা করে। এই পাইপলাইনটি আমাদের CI সিস্টেমকে "Self-Healing" ক্ষমতা প্রদান করে।

---

## 🎯 মূল উদ্দেশ্য: স্বয়ংক্রিয় কোড মেরামত

এই ওয়ার্কফ্লোর প্রধান লক্ষ্য হলো `supreme-ci.yml` (কোর সিআই) পাইপলাইনে সাধারণ কিছু ব্যর্থতা (যেমন: লিಂಟিং, ফরম্যাটিং, বা নির্ভরতা সংক্রান্ত সমস্যা) স্বয়ংক্রিয়ভাবে সমাধান করা। যখন কোনো ডেভেলপার কোড পুশ করেন এবং CI কোনো সাধারণ ত্রুটির কারণে ব্যর্থ হয়, তখন এই ওয়ার্কফ্লোটি নিজে থেকে সেই সমস্যা সমাধান করে একটি নতুন Pull Request (PR) তৈরি করে। এর ফলে, ডেভেলপারদের ম্যানুয়ালি ছোটখাটো ভুল সংশোধন করতে হয় না এবং তারা মূল কাজে মনোযোগ দিতে পারেন।

---

## 🚀 ওয়ার্কফ্লো ট্রিগার

এই ওয়ার্কফ্লোটি দুটি প্রধান উপায়ে চালু হতে পারে:

1.  **`workflow_run` (স্বয়ংক্রিয়):**
    -   **শর্ত:** যখন `supreme-ci.yml` ওয়ার্কফ্লোটি `failure` স্ট্যাটাস দিয়ে শেষ হয়।
    -   **কাজ:** এটি স্বয়ংক্রিয়ভাবে ট্রিগার হয় এবং ব্যর্থ হওয়া জবগুলোর তালিকা নিয়ে কাজ শুরু করে।

2.  **`workflow_dispatch` (ম্যানুয়াল):**
    -   **কাজ:** GitHub Actions UI থেকে যেকোনো ব্রাঞ্চের উপর ম্যানুয়ালি চালানো যায়।
    -   **ইনপুট:** ম্যানুয়ালি চালানোর সময় `failed_jobs` নামে একটি JSON অ্যারে ইনপুট দেওয়া যায়, যেখানে নির্দিষ্ট জবের নাম (যেমন: `["backend-test", "studio-build"]`) উল্লেখ করে দেওয়া যায়। যদি কোনো ইনপুট না দেওয়া হয়, তবে এটি রিপোজিটরির সমস্ত প্যাকেজের জন্য ফিক্সার চালানোর চেষ্টা করে।

## 🛠️ প্রধান জব এবং তাদের কার্যকারিতা

ওয়ার্কফ্লোটি মূলত একটি প্রধান জবের মাধ্যমে কাজ করে, যা `ci-auto-fix.py` স্ক্রিপ্টটি চালায়।

-   **জব:** `auto-fix`
-   **কাজ:** এই জবটি কয়েকটি ধাপে বিভক্ত:

    1.  **ব্যর্থ জব শনাক্তকরণ:**
        -   যদি ওয়ার্কফ্লোটি স্বয়ংক্রিয়ভাবে (`workflow_run`) চালু হয়, তবে এটি পূর্ববর্তী `supreme-ci.yml` রানের `ci-report` আর্টিফ্যাক্টটি ডাউনলোড করে এবং সেখান থেকে ব্যর্থ জবগুলোর তালিকা বের করে।
        -   যদি ম্যানুয়ালি (`workflow_dispatch`) চালানো হয়, তবে এটি `failed_jobs` ইনপুট থেকে জবের তালিকা নেয়।

    2.  **ফিক্সার চালানো (`ci-auto-fix.py`):**
        -   শনাক্ত হওয়া প্রতিটি ব্যর্থ জবের জন্য, স্ক্রিপ্টটি একটি নির্দিষ্ট ফিক্সার ফাংশন চালায়।
        -   **Backend (`fix_backend`):**
            -   `ruff check --fix`: লিಂಟিং সমস্যা সমাধান করে।
            -   `black .`: কোড ফরম্যাট করে।
            -   `ensure_init_files`: প্রয়োজনীয় `__init__.py` ফাইল তৈরি করে।
            -   `poetry lock --no-update`: `poetry.lock` ফাইল সিঙ্ক করে।
        -   **Frontend (`fix_frontend`):**
            -   `eslint --fix`: জাভাস্ক্রিপ্ট/টাইপস্ক্রিপ্ট লিಂಟিং সমস্যা সমাধান করে।
            -   `prettier --write`: কোড ফরম্যাট করে।
            -   `pnpm install`: `pnpm-lock.yaml` ফাইল সিঙ্ক করে।
        -   **Mobile (`fix_mobile`):**
            -   `dart fix --apply`: ডার্ট কোডের সমস্যা সমাধান করে।
            -   `dart format .`: কোড ফরম্যাট করে।
            -   `flutter pub get`: `pubspec.lock` ফাইল সিঙ্ক করে।

    3.  **নিরাপত্তা পরীক্ষা (`Diff Guard`):**
        -   ফিক্সারগুলো চালানোর পর, কোডে কী কী পরিবর্তন হয়েছে তা পরীক্ষা করার জন্য `guard_check()` ফাংশনটি চালানো হয়।
        -   এটি নিশ্চিত করে যে পরিবর্তনগুলো নিরাপদ এবং নির্দিষ্ট সীমার মধ্যে আছে:
            -   **`MAX_FILES_CHANGED` (১০):** ১০টির বেশি ফাইল পরিবর্তন হলে প্রক্রিয়াটি বন্ধ হয়ে যাবে।
            -   **`MAX_LINES_CHANGED` (৩০০):** ৩০০ লাইনের বেশি কোড পরিবর্তন হলে প্রক্রিয়াটি বন্ধ হয়ে যাবে।
            -   **`CRITICAL_FILE_PATTERNS`:** `core/auth`, `core/security` বা ডেটাবেস মাইগ্রেশনের মতো সংবেদনশীল ফাইলগুলোতে কোনো স্ট্রাকচারাল পরিবর্তন করার চেষ্টা করলে প্রক্রিয়াটি ব্লক হয়ে যায়।
        -   যদি `Diff Guard` ব্যর্থ হয়, তবে এটি স্বয়ংক্রিয়ভাবে একটি GitHub Issue তৈরি করে এবং অ্যাডমিনকে পর্যালোচনার জন্য অবহিত করে।

    4.  **Pull Request (PR) তৈরি:**
        -   `Diff Guard` সফল হলে, স্ক্রিপ্টটি `auto-fix/<branch>-<timestamp>` নামে একটি নতুন ব্রাঞ্চ তৈরি করে।
        -   পরিবর্তিত কোড কমিট করে এবং মূল ব্রাঞ্চকে টার্গেট করে একটি Pull Request তৈরি করে।
        -   কমিট মেসেজে `[skip ci]` যোগ করা হয়, যাতে এই কমিটটি আবার CI ট্রিগার না করে একটি অসীম লুপ তৈরি করে।

## 🔄 `Core CI`-এর সাথে পুনরায় ইন্টিগ্রেশন

`maintenance_pipeline.yml` সফলভাবে একটি PR তৈরি করার পর, অ্যাডমিন সেই PR-টি রিভিউ এবং মার্জ করতে পারেন। মার্জ করার পর, `Core CI` (`supreme-ci.yml`) আবার নতুন করে চলে এবং এবার আশা করা যায় যে সমস্ত জব সফলভাবে পাশ করবে।

যদি অটো-ফিক্স প্রক্রিয়াটি ব্যর্থ জবগুলোকে পুনরায় চালানোর জন্য `Core CI`-কে ট্রিগার করত (যেমনটি `supreme-ci-auto-fix.yml` করে), তবে এটি `forced_jobs` ইনপুট ব্যবহার করত, যাতে শুধুমাত্র ব্যর্থ হওয়া জবগুলোই আবার চলে।

## 🛡️ নিরাপত্তা এবং স্থিতিশীলতা (Safety Guards)

এই ওয়ার্কফ্লোতে বেশ কিছু শক্তিশালী নিরাপত্তা ব্যবস্থা রয়েছে:

-   **Diff Guard:** অতিরিক্ত বা বিপজ্জনক কোড পরিবর্তন প্রতিরোধ করে।
-   **Critical File Protection:** সংবেদনশীল ফাইলগুলোতে স্বয়ংক্রিয় পরিবর্তন ব্লক করে।
-   **No Infinite Loops:** যদি ফিক্সার স্ক্রিপ্ট কোনো পরিবর্তন করতে না পারে, তবে এটি অসীম লুপে আটকে না গিয়ে প্রক্রিয়াটি বন্ধ করে দেয় এবং একটি ইস্যু তৈরি করে।
-   **Pull Request Model:** সরাসরি মূল ব্রাঞ্চে পুশ না করে, এটি একটি PR তৈরি করে, যা মানুষকে পর্যালোচনার সুযোগ দেয়।

এই পাইপলাইনটি আমাদের ডেভেলপমেন্ট প্রক্রিয়াকে দ্রুততর এবং আরও নির্ভরযোগ্য করে তুলেছে।
