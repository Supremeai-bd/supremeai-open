# 📖 SupremeAI Smart CI/CD ওয়ার্কফ্লো (`supreme-ci.yml`)

এই ডকুমেন্টটি আমাদের প্রধান CI/CD (Continuous Integration/Continuous Deployment) পাইপলাইন `supreme-ci.yml`-এর কার্যকারিতা, বিভিন্ন ধাপ এবং এর পেছনের মূল ধারণাগুলো ব্যাখ্যা করে।

---

## 🎯 মূল উদ্দেশ্য: "Self-Healing" পাইপলাইন

আমাদের CI/CD সিস্টেমের প্রধান লক্ষ্য হলো **"সাইলেন্ট ফেইলিওর" (Silent Failure)** প্রতিরোধ করা।

**সমস্যা:** সাধারণ CI সিস্টেমে, যদি কোনো একটি জব (যেমন: `backend-test`) একবার ব্যর্থ হয় এবং পরবর্তী পুশ-এ সেই জবের সাথে সম্পর্কিত কোনো ফাইল পরিবর্তন না করা হয়, তাহলে CI সিস্টেম সেই ব্যর্থ জবটি এড়িয়ে (skip) যায়। এর ফলে, ошибкаটি ডেভেলপার ঠিক করেছেন কিনা তা যাচাই করার কোনো সুযোগ থাকে না এবং এটি প্রোডাকশনে চলে যাওয়ার ঝুঁকি তৈরি করে।

**আমাদের সমাধান:** `supreme-ci.yml` একটি **"Failure-Aware"** বা **"Self-Healing"** পাইপলাইন। যদি কোনো জব একবার ব্যর্থ হয়, তবে এটি সফল না হওয়া পর্যন্ত প্রতিটি নতুন ট্রিগারে স্বয়ংক্রিয়ভাবে পুনরায় চালানোর জন্য বাধ্য করা হয়, এমনকি যদি সংশ্লিষ্ট ফাইলগুলোতে কোনো পরিবর্তন নাও থাকে।

---

## 🚀 ওয়ার্কফ্লো ট্রিগার

এই ওয়ার্কফ্লোটি নিম্নলিখিত ঘটনাগুলোর উপর ভিত্তি করে চালু হয়:

1.  **`push`**: `main`, `master`, বা `develop` ব্রাঞ্চে কোড পুশ করা হলে।
2.  **`pull_request`**: `main`, `master`, বা `develop` ব্রাঞ্চকে টার্গেট করে কোনো Pull Request তৈরি বা আপডেট করা হলে।
3.  **`workflow_dispatch`**: GitHub Actions UI থেকে ম্যানুয়ালি চালানো হলে।

### ম্যানুয়াল ইনপুট (`workflow_dispatch`)

ম্যানুয়ালি চালানোর সময় কিছু অতিরিক্ত অপশন দেওয়া যায়:

-   **`forced_jobs`**: একটি JSON অ্যারে, যেখানে নির্দিষ্ট জবের আইডি (`backend-test`, `studio-build`) দিয়ে দেওয়া যায়, যা আপনি কোনো শর্ত ছাড়াই চালাতে চান। এটি মূলত অটো-ফিক্স প্রক্রিয়া ব্যবহার করে।
-   **`is_retry`**: এটি একটি `true`/`false` ফ্ল্যাগ যা নির্দেশ করে এই রানটি কোনো অটো-ফিক্স প্রক্রিয়ার অংশ কিনা।

## 🛠️ প্রধান জব এবং তাদের কার্যকারিতা

ওয়ার্কফ্লোটি কয়েকটি ধাপে বিভক্ত, যা পর্যায়ক্রমে চলে:

### ধাপ ১: স্বাস্থ্য পরীক্ষা (Health Check)

-   **জব:** `ci-health-check`
-   **কাজ:** পাইপলাইনের মূল কাজ শুরু করার আগে এটি আমাদের সিস্টেমের স্বাস্থ্য পরীক্ষা করে। এটি নিশ্চিত করে যে SupremeAI API এবং এর ব্যাকআপ সার্ভারগুলো সচল আছে। যদি কোনো একটি সিস্টেম ডাউন থাকে, তবে এটি স্বয়ংক্রিয়ভাবে বাহ্যিক AI প্রদানকারী (যেমন: OpenAI, Gemini) ব্যবহার করার জন্য নিজেকে প্রস্তুত করে।

### ধাপ ২: পরিবর্তন এবং পূর্ববর্তী ব্যর্থতা সনাক্তকরণ

এই ধাপে দুটি সমান্তরাল জব চলে:

1.  **`detect-changes`**:
    -   **কাজ:** রিপোজিটরির কোন অংশে (`backend`, `studio`, `mobile` ইত্যাদি) পরিবর্তন হয়েছে তা শনাক্ত করে।

2.  **`check-previous-failures`**:
    -   **কাজ:** এটি আমাদের "স্মার্ট রিট্রাই" সিস্টেমের মস্তিষ্ক। এই জবটি `.github/scripts/detect-previous-failures.py` স্ক্রিপ্টটি চালায়।
    -   **স্ক্রিপ্টের কার্যকারিতা:**
        -   GitHub API ব্যবহার করে বর্তমান ব্রাঞ্চের পূর্ববর্তী CI রানগুলোর ইতিহাস (শেষ ৫০টি) পরীক্ষা করে।
        -   প্রতিটি জবের স্ট্যাটাস (`success`, `failure`, `cancelled`, `timed_out`) বিশ্লেষণ করে।
        -   যদি কোনো জব আগে ব্যর্থ (`failure`, `cancelled`, `timed_out`) হয়ে থাকে এবং তারপর থেকে সফলভাবে রান না করে, তবে সেই জবের জন্য একটি "ফোর্স ফ্ল্যাগ" (যেমন: `backend_force=true`) তৈরি করে।

### ধাপ ৩: সিদ্ধান্ত গ্রহণ (Combine Decisions)

-   **জব:** `combine-decisions`
-   **কাজ:** এই জবটি `detect-changes` এবং `check-previous-failures` থেকে প্রাপ্ত আউটপুট এবং `workflow_dispatch` থেকে আসা `forced_jobs` ইনপুট একত্রিত করে চূড়ান্ত সিদ্ধান্ত নেয়।
-   **সিদ্ধান্তের যুক্তি:** একটি জব (`<pkg>_run`) তখনই `true` হবে যদি:
    -   `(<pkg>_changed == 'true')` **অথবা**
    -   `(<pkg>_force == 'true')` **অথবা**
    -   `(<pkg> is in forced_jobs)`

### ধাপ ৪: মূল বিল্ড এবং টেস্ট জবসমূহ

এই জবগুলো `combine-decisions`-এর সিদ্ধান্তের উপর ভিত্তি করে চলে। প্রতিটি জব `if: needs.combine-decisions.outputs.<job_name>_run == 'true'` শর্ত দিয়ে সুরক্ষিত।

-   `backend-test`: ব্যাকএন্ডের ইউনিট টেস্ট এবং ইন্টিগ্রেশন টেস্ট চালায়।
-   `studio-build`: স্টুডিও ক্লায়েন্টের প্রোডাকশন বিল্ড তৈরি করে।
-   `mobile-analyze`: মোবাইল অ্যাপের কোড বিশ্লেষণ এবং লিंटিং করে।
-   `webchat-build`: ওয়েব-চ্যাট অ্যাপের প্রোডাকশন বিল্ড তৈরি করে।
-   `vscode-build`: VS Code এক্সটেনশনের প্রোডাকশন বিল্ড তৈরি করে।
-   `prompt-eval`: LLM প্রম্পটগুলোর কার্যকারিতা মূল্যায়ন করে।

### ধাপ ৫: রিপোর্ট তৈরি

-   **জব:** `ci-report`
-   **কাজ:** পাইপলাইনের সমস্ত জবের স্ট্যাটাস (`success`, `failure`, `skipped`) সংগ্রহ করে একটি 종합 রিপোর্ট তৈরি করে। এই রিপোর্টটি `ci-report` নামে একটি আর্টিফ্যাক্ট হিসেবে আপলোড করা হয়, যা পরবর্তী অটো-ফিক্স ওয়ার্কফ্লো ব্যবহার করে।

## 🔄 অটো-ফিক্স ওয়ার্কফ্লোর সাথে ইন্টিগ্রেশন

`supreme-ci.yml` ওয়ার্কফ্লো যদি ব্যর্থ হয়, তবে এটি স্বয়ংক্রিয়ভাবে `supreme-ci-auto-fix.yml` নামক অন্য একটি ওয়ার্কফ্লোকে ট্রিগার করে।

1.  **ট্রিগার:** `supreme-ci.yml`-এর রান `failure` স্ট্যাটাস দিয়ে শেষ হলে।
2.  **অটো-ফিক্স:** `supreme-ci-auto-fix.yml` ওয়ার্কফ্লোটি `ci-report` আর্টিফ্যাক্টটি ডাউনলোড করে ব্যর্থ জবগুলো শনাক্ত করে।
3.  **সমাধান:** প্রতিটি ব্যর্থ জবের জন্য নির্দিষ্ট ফিক্সার (যেমন: `ruff --fix`, `eslint --fix`) চালায় এবং কোড পরিবর্তন করে একটি নতুন ব্রাঞ্চে কমিট করে।
4.  **পুনরায় ট্রিগার:** এরপর, অটো-ফিক্স ওয়ার্কফ্লোটি `supreme-ci.yml`-কে আবার `workflow_dispatch` ইভেন্টের মাধ্যমে ট্রিগার করে এবং `forced_jobs` ইনপুটে শুধুমাত্র সেই ব্যর্থ জবগুলোর নাম পাঠিয়ে দেয়।

এর ফলে, পরবর্তী রানে শুধুমাত্র ব্যর্থ হওয়া জবগুলোই আবার চলে, যা রিসোর্সের অপচয় রোধ করে।

## 🛡️ নিরাপত্তা এবং স্থিতিশীলতা (Safety Guards)

আমাদের CI সিস্টেমে বেশ কিছু নিরাপত্তা স্তর রয়েছে:

-   **API Health Check:** কোনো সিস্টেম ডাউন থাকলে CI শুরুতেই সতর্ক করে দেয়।
-   **Diff Guard:** অটো-ফিক্স প্রক্রিয়া যদি অতিরিক্ত ফাইল বা লাইন পরিবর্তন করার চেষ্টা করে, তবে তা ব্লক হয়ে যায় এবং একটি GitHub Issue তৈরি হয়।
-   **Critical File Protection:** `core/auth`, `core/security` এর মতো ক্রিটিক্যাল ফাইলগুলোতে কোনো স্ট্রাকচারাল পরিবর্তন করার আগে অ্যাডমিনের অনুমোদন প্রয়োজন হয়।
-   **Infinite Loop Protection:** অটো-ফিক্স স্ক্রিপ্ট যদি পরপর কয়েকবার ব্যর্থ হয়, তবে এটি অসীম লুপে আটকে না গিয়ে পাইপলাইন বন্ধ করে দেয়।

## 📊 সিদ্ধান্ত ম্যাট্রিক্স (কখন কী হয়)

| পরিস্থিতি | ফাইল পরিবর্তন? | পূর্ববর্তী রান | চূড়ান্ত সিদ্ধান্ত | কারণ |
|:---|:---:|:---:|:---:|:---|
| ১ | `backend` ✅ | সফল | **RUN** | স্বাভাবিক পরিবর্তন। |
| ২ | `backend` ❌ | সফল | **SKIP** | কোনো পরিবর্তন নেই এবং আগে সফল ছিল। |
| ৩ | `backend` ❌ | ব্যর্থ | **RUN** | "স্মার্ট রিট্রাই" - ব্যর্থ জব পুনরায় চালানো হচ্ছে। |
| ৪ | `backend` ❌ | এড়িয়ে গেছে (Skipped) | **RUN** | যেহেতু আগেরবার স্কিপ হয়েছিল, তাই তারও আগের ব্যর্থ স্ট্যাটাসটি বিবেচনায় আনা হয়েছে। |
| ৫ | `frontend` ✅ | `backend` ব্যর্থ | **RUN BOTH** | `frontend` চলবে কারণ ফাইল পরিবর্তন হয়েছে এবং `backend` চলবে কারণ এটি আগে ব্যর্থ হয়েছিল। |

এই স্মার্ট সিস্টেমটি নিশ্চিত করে যে আমাদের কোডবেস সর্বদা একটি সুস্থ এবং নির্ভরযোগ্য অবস্থায় থাকে।
